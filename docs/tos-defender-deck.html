Architecture

Four browser pieces, one API, two AI providers

The extension never calls an AI provider directly. Everything goes through the local FastAPI server, which owns prompts, keys, and evidence checks.

Architecture3

End-to-end run

What happens after “Check this page's terms”

The current page is checked first. Links are classified in one batch, and only the ones judged to be legal documents are fetched and analyzed, three at a time.

Sequence4

Step 1 · Link discovery

Turning the page into a candidate list

The content script reads every anchor and keeps only links worth asking about. Labels and URLs are all Jev ever sees at this stage. No page content is sent.

Current page goes first

If the page you're on is itself a policy, its own text is read from the DOM and analyzed. A small corner pill opens its summary.

Dynamic pages

A MutationObserver notices new links after load and schedules another pass, debounced at 250 ms. It ignores the extension's own nodes.

Every run is isolated

Each run gets a runId. Late responses from an older run are dropped, so restarting never mixes results.

Step 2 · Classification with Jev

One yes/no question per link, all in parallel

Jev never sees question IDs. The first version asked the same question N times about the whole list, so every link "contained" the privacy policy. Now each question carries its own link.

Before · every link ≈ 95% policy

After · each question is self-contained

questions:

      link: { label, url },
      question: "Is the destination of `link` itself
        a legal or policy document…?" },
    criteria={ true: […], false: […] })
  type_i:  Choice(terms · privacy · billing · other)

Step 3 · Reading the document

From HTML to numbered passages

Admitted links are fetched with the user's own session, and the page chrome is stripped away. The server then splits the text into passages with stable IDs, so every finding can point back to its source.

content.js · extractText · apps/api/text.py7

Step 4 · Staged analysis

Fast answer first, verified answer second

One streaming request. A quick scan of the most relevant passages produces a provisional shield in seconds. The stream then stays open while the full review reads every passage and checks each claim.

server.py · analyze_staged · pipeline.analyze_fast / analyze8

Step 5 · Evidence guards

A finding must survive three filters

The LLM may draft anything. Only points that quote the document exactly, stay concise, and are judged as supported by the quoted passage reach the user.

pipeline.py · _verified_citation · verify_claims9

Step 6 · Impact rating

How each point affects the person accepting it

One Jev request with one Score question per finding, on a four-level rubric. Code buckets the expected score and rolls the worst level up into the shield color.

Rollup → shield

any Important → “Read before you accept”
else any Worth checking → “Some terms worth checking”
else rated findings → “No major concerns found”
nothing rated → “No notable terms verified”
Score(instructions={
  finding: { summary, consequence, quote },
  question: "How does `finding` affect the person
    who accepts this document…?" },
  criteria=[favor, routine, worth checking, important])
Analysis.rating is a computed field · rating failures
leave findings intact and the shield unrated

Operations

Observability, privacy, and safety

Every hop is logged with correlation IDs, without logging policy text. Access is requested per site, and nothing from the page is ever rendered as HTML.

Correlated logs

Privacy by design

  • Site access is an optional permission, requested per origin on click
  • Runs only when you ask, never in the background
  • Classification sends link labels and URLs only
  • Logs carry origin + path, never query strings or policy text
  • Policy pages are fetched same-origin with your own session
  • Status is cleared when the tab closes

Robustness

  • Policy text is treated as untrusted data in every prompt
  • All UI built with textContent, never innerHTML
  • Closed Shadow DOM isolates styles both ways
  • Stale runs dropped by runId; streams aborted on restart
  • Full-review failure keeps the provisional summary
  • Rating failure keeps findings, shield shows unrated

Where it goes next

Limits today, options tomorrow

Current limits

• Same-origin links only. Policies hosted on another domain are skipped.
• Manual trigger: the user has to open the popup and click.
• Borderline pages (Trust Center 0.29, Security 0.42) fall under the 0.7 threshold.
• Pages that render policies client-side may give too little text when fetched.
• The API runs locally at localhost:8000.

Natural next steps

• Auto-detect consent checkboxes and offer a check right there.
• Allow trusted cross-origin legal hosts (e.g. a separate legal subdomain).
• Cache results per document hash so repeat visits are instant.
• “Ask this document” in the panel, using the existing /api/ask.
• Evaluate rating thresholds on a labeled set of real policies.
